# 排产系统规划 v2（现状校准版）

> **版本**：v2.1
> **状态**：按当前代码现状重整，可直接用于实施对齐
> **适用范围**：生产协同中心排产域，覆盖 `frontend/src/pages/ProductionCenter/*` 与 `backend/app/api/v1/production/*`
> **核心判断**：当前不是“从零重构排产系统”，而是“页面级拆分已完成，领域级收口还差一轮”

---

## 一、文档目的

本版不再重复早期规划里已经落地的部分，重点做三件事：

1. 校准排产模块当前已经具备的真实能力边界。
2. 区分“已完成 / 半完成 / 未完成”，避免后续按旧认知推进。
3. 输出可直接执行的下一阶段实施方案、文件任务表、风险与验收标准。

## 三、现状与规划差距

### 3.1 前端差距

当前最大问题已经不是“没有页面”，而是“页面虽已拆，编排还没收口”。

| 差距项 | 当前现状 | 影响 |
|---|---|---|
| 排产台账仍是巨型中心 | `SchedulePlans/index.tsx` 仍保留 `planner_hub / change_events / schedule_board` 等遗留分支 | 状态过重，回归风险高 |
| 页面与页面之间协议未统一 | 跳转参数在多个页面分散维护 | 后续扩展容易失配 |
| 刷新 / 缓存 / 失效逻辑仍在页面内 | `cacheRef / inflightRef / skipSnapshotReconcile` 仍侵入 UI 组件 | 性能优化难复用 |
| API 引用双入口并存 | 页面有的走 `services/api.ts`，有的走 `services/production.ts` | 未来维护成本高 |
| 共享层停留在 helper / modal | 还没有稳定的排产 domain hooks 层 | 新需求仍容易回灌到台账页 |
| 看板数据层未独立 | 看板仍依赖计划列表接口再前端重组 | 展示独立了，数据口径还没完全独立 |

### 3.2 后端差距

当前后端主链路已成型，缺口主要集中在“补齐、稳定、配置化”，不是推翻重建。

| 差距项 | 当前现状 | 影响 |
|---|---|---|
| 缺少 UPPH 产品清单 | `/missing-upph-products` 仍直接返回“优化中，暂时不可用” | 产能治理闭环不完整 |
| 372 KPI 仍是半成品 | `frozen_break_count=0`、`kit_ready_rate=1.0`、`shortage_count=0`、`eta_delay_count=0`、`anomalies=[]` 为占位 | 驾驶舱可展示但不可运营 |
| 删除补位仍是一期方案 | 以释放窗口 + 顺延候选为主，不是完整智能重算 | 复杂场景稳定性仍有限 |
| 变更事件未独立持久化 | 当前更偏日志式动态重算与缓存 | 规模上来后追溯和性能都会受影响 |
| 工时与规则仍偏硬编码 | `config_service.py` 仍以默认配置为主 | 业务规则调整成本偏高 |
| 冷冻区闭环不完整 | 已有 `time_zone` 过滤与理由校验，但完整提权、留痕、干预统计还未形成闭环 | 372 中黄区仍不够硬 |

### 3.3 372 规划差距

372 的方向是成立的，但当前处于“可用版”而不是“闭环版”。

| 维度 | 当前状态 | 下一步 |
|---|---|---|
| 驾驶舱页面 | 已有首版 | 补全 KPI、异常、联动口径 |
| 三栏结构 | 已体现雏形 | 继续统一今日 / 冷冻 / 配料的数据定义 |
| 管理态势条 / 抽屉 | 未做 | 需要在领域收口后再挂载 |
| 配料区物料视角 | 未做 | 需接齐套与物料需求数据 |
| 冷冻区强管控 | 未做完整 | 需补提权、理由、留痕、统计 |

## 四、实施原则

### 4.1 总原则

- 不推倒重来，基于现有页面拆分成果继续下沉和收口。
- 先收口前端边界，再补驾驶舱闭环，最后增强后端配置化与持久化。
- 优先解决高风险高收益问题，不同时开启过多重构面。

### 4.2 关键规则

| 规则 | 说明 |
|---|---|
| `time_zone` 动态派生 | 必须按查询时计算，不作为持久化字段写库 |
| “排产台账”单一职责 | `SchedulePlans` 只承接计划台账，不再继续兼容已独立出去的旧 workspace 结构 |
| 统一 API 入口 | 前端排产相关接口统一收口到 `frontend/src/services/production.ts` |
| 统一导航协议 | 驾驶舱、工作台、台账、看板共用一套路由参数协议 |
| 操作后置动作统一 | 删除、重排、排产成功后的刷新、失效、跳转走同一套 orchestration |
| KPI 逐步补齐 | 未接通字段明确显示占位，不伪造真实结果 |

## 五、分阶段改造方案

### 阶段 1：台账瘦身

**目标**：把 `SchedulePlans` 收成真正的“排产台账页”。

**核心动作**：

- 清理已经被独立页面替代的 `planner_hub / change_events / schedule_board` 遗留分支。
- 抽出 `usePlanBoard`、`usePlanRouting`、`usePlanMutations` 等 hooks。
- 将详情抽屉、历史、日志、删除、重排等操作改为围绕台账职责组织。

**预期收益**：

- 降低巨型组件维护成本。
- 新增功能不再继续堆进单文件。
- 为后续统一共享层与态势条打基础。

### 阶段 2：共享层统一

**目标**：把排产域从“页面拆分”推进到“领域收口”。

**核心动作**：

- 将当前散落在 `SchedulePlans` 下的通用常量、类型、跳转协议提升到 `ProductionCenter` 级公共层。
- 统一所有排产页的 API 引用到 `services/production.ts`。
- 将刷新、缓存失效、成功回跳、消息提示统一到 mutation orchestration 层。

**预期收益**：

- 待排、变更、台账、看板之间的耦合明显下降。
- 后续做 372 联动时不需要重复拼业务协议。

### 阶段 3：372 驾驶舱闭环

**目标**：让驾驶舱从“可展示”升级为“可运营入口”。

**核心动作**：

- 补全 `kpi-summary` 中冷冻区、配料区、异常清单等真实指标。
- 统一驾驶舱、台账、看板之间的口径与定位参数。
- 视前端收口结果，评估是否接入管理态势条与抽屉。

**预期收益**：

- 372 不再只是首版展示页，而成为排产域入口页。
- 用户可以围绕今日、冷冻、配料三区完成定位和处理。

### 阶段 4：后端增强

**目标**：补强当前已经暴露的真实瓶颈。

**核心动作**：

- 恢复缺 UPPH 产品列表接口。
- 优化删除补位链路，稳定控制在 2 秒目标内。
- 视业务需要推进变更事件持久化、规则配置化、冷冻干预统计。

**预期收益**：

- 系统解释性、稳定性和可运营性提升。
- 后端增强围绕真实瓶颈展开，不做无效大改。

## 七、风险与验收标准

### 7.1 当前主要风险

| 风险项 | 说明 | 应对 |
|---|---|---|
| 巨型组件持续膨胀 | 若不先做台账瘦身，新需求仍会继续堆回 `SchedulePlans` | 阶段 1 优先处理 |
| 删除链路误报 | 删除成功后若刷新失败，用户感知仍可能是“删除失败 / 网络错误” | 阶段 2 统一 mutation 后置动作 |
| KPI 口径失真 | 当前多个 KPI 仍是占位值 | 阶段 3 前必须补真实口径 |
| API 双入口漂移 | `api.ts` 与 `production.ts` 并行使用会产生重复封装 | 阶段 2 统一 |
| 看板数据层耦合 | 看板展示独立但数据还依赖台账接口 | 阶段 2-3 逐步收口 |

### 7.2 验收标准

| 阶段 | 验收标准 |
|---|---|
| 阶段 1 | `SchedulePlans` 不再承载已独立页面的旧 workspace 分支 |
| 阶段 1 | 页面间定位参数协议统一，回流定位不靠散落拼接 |
| 阶段 2 | 删除、重排、排产成功后的刷新、提示、跳转走统一编排 |
| 阶段 2 | 排产相关前端接口统一从 `services/production.ts` 导出 |
| 阶段 3 | `kpi-summary` 不再用 `kit_ready_rate=1.0`、`shortage_count=0`、`anomalies=[]` 等占位冒充真实数据 |
| 阶段 3 | 驾驶舱、台账、看板共享同一套三区口径和定位参数 |
| 阶段 4 | 缺 UPPH 产品清单可正常使用，不再返回“优化中” |
| 阶段 4 | 删除补位链路满足 2 秒级目标，且异常提示与真实结果一致 |

## 八、建议执行顺序

建议按下面顺序推进，不再继续扩页面数量：

1. 先做台账瘦身，把 `SchedulePlans` 收成真正的“排产台账”。
2. 再做共享层统一，把导航、缓存失效、成功后动作抽成领域层能力。
3. 然后补 372 驾驶舱 KPI 和异常闭环。
4. 最后再做后端增强，如事件持久化、规则配置化、补位策略升级。

## 九、结论

当前排产模块的真实状态可以概括为：

- 已完成：页面级拆分、基础跳转闭环、看板独立、变更中心独立、排产主链路后端骨架、UPPH/产能治理。
- 半完成：排产台账瘦身、统一共享层、372 KPI 口径、删除链路稳定性。
- 未完成：真正的 domain hooks 层、ProductionCenter 公共层、态势条与抽屉闭环、事件持久化、规则配置化。

因此，下一阶段的核心不是“重做排产系统”，而是：

**在现有结构上继续收口、统一协议、补齐闭环。**
