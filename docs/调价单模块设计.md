# 调价单模块 · 完整设计

> **版本**：v1.2
> **日期**：2026-07-09
> **状态**：规划阶段，待开发
> **核心理念**：从泛微OA迁移到自建系统，字段对齐OA，审批流内嵌，AI辅助决策，审批通过自动同步ERP
>
> **v1.2 变更**：补审批快照、submitted_at 字段、草稿逻辑、实施计划调整、优先级定义

## 一、模块定位

```
采购调价单 = 采购域独立子模块
和排产系统完全独立，只有共用基础设施（登录/权限/前端框架/axios）

数据来源：
  ├── 供应商 → scm_supplier（1787 条，从 ERP 同步）
  ├── 物料   → scm_material（从 ERP 同步）
  └── 历史价 → purchase_order（7523 条，取最近采购价）

产出去向：
  └── 审批通过 → 同步 ERP（更新物料采购价）
```

## 二、数据库设计

### 主表 `purchase_price_change`

```sql
CREATE TABLE purchase_price_change (
  id              SERIAL PRIMARY KEY,
  change_no       VARCHAR(32) NOT NULL UNIQUE,    -- 单据编号（PC+日期+序号）
  title           VARCHAR(256),                   -- 标题
  change_type     VARCHAR(32) DEFAULT 'price_change', -- 类型
  price_direction VARCHAR(16),                    -- 涨价/降价/新报价

  -- 供应商信息（从 scm_supplier 下拉选，自动带出）
  supplier_code   VARCHAR(64),                    -- 供应商代码
  supplier_name   VARCHAR(128),                   -- 供应商名称
  phone           VARCHAR(32),                    -- 电话
  fax             VARCHAR(32),                    -- 传真
  contact_person  VARCHAR(64),                    -- 联系人
  address         VARCHAR(256),                   -- 地址

  -- 顾客信息
  customer        VARCHAR(128),                   -- 顾客
  customer_phone  VARCHAR(32),                    -- 顾客电话
  customer_fax    VARCHAR(32),                    -- 顾客传真
  purchase_contact VARCHAR(64),                   -- 采购联系人

  -- 财务信息
  tax_rate        VARCHAR(16),                    -- 税率
  payment_method  VARCHAR(64),                    -- 付款方式
  settlement_method VARCHAR(64),                  -- 结算方式

  -- 日期
  change_date     DATE,                           -- 调价日期

  -- 附件（多文件，JSON 数组）
  attachments     JSONB DEFAULT '[]',             -- [{"name":"xxx.pdf","size":1024,"url":"/uploads/..."}]

  -- 备注 + 签字
  remark          TEXT,                           -- 备注
  signature_opinion TEXT,                         -- 签字意见

  -- 审批
  approval_status VARCHAR(16) DEFAULT 'draft',    -- draft/pending/approved/rejected/recalled
  approval_level  INT DEFAULT 1,                  -- 当前审批级别（1-4）
  approved_by     VARCHAR(64),                    -- 最终审批人
  approved_at     TIMESTAMP,                      -- 最终审批时间
  submitted_at    TIMESTAMP,                      -- 首次提交审批时间（用于超时催办）
  approval_snapshot JSONB,                        -- 发起审批时的完整审批链快照（JSON，供日志追溯）
  version         INT DEFAULT 1,                  -- 乐观锁版本号（防止并发审批冲突）

  -- ERP 同步
  erp_sync_status VARCHAR(16) DEFAULT 'pending',  -- pending/synced/failed/skipped
  erp_sync_at     TIMESTAMP,
  erp_error_msg   TEXT,

  -- 审计
  applicant       VARCHAR(64),                    -- 申请人
  created_at      TIMESTAMP DEFAULT NOW(),
  updated_at      TIMESTAMP DEFAULT NOW()
);
```

### 子表 `purchase_price_change_item`

```sql
CREATE TABLE purchase_price_change_item (
  id              SERIAL PRIMARY KEY,
  change_id       INT NOT NULL REFERENCES purchase_price_change(id) ON DELETE CASCADE,
  seq             INT,                            -- 序号

  -- 物料信息（从 scm_material 下拉选自动带出）
  material_code   VARCHAR(64),                    -- 物料代码
  material_name   VARCHAR(256),                   -- 物料名称
  spec            VARCHAR(256),                   -- 规格
  unit            VARCHAR(16),                    -- 单位

  -- 数量
  order_qty       NUMERIC(15,4),                  -- 订货量
  delivery_qty    NUMERIC(15,4),                  -- 订货量到/到货量

  -- 价格
  old_price       NUMERIC(15,4),                  -- 原价
  old_price_date  VARCHAR(16),                    -- 原价年月
  new_price       NUMERIC(15,4),                  -- 现价
  price_change_pct NUMERIC(5,2),                  -- 涨幅%（自动算：old为空或0时显示'--'）
> **涨幅计算防御**：old_price 为空或为 0 时，涨幅字段设为 null，前端显示 "--"。前后端都做零值校验，避免除零错误。

  remark          VARCHAR(256)                    -- 备注
);
```

### 审批日志 `purchase_price_change_approval_log`

```sql
CREATE TABLE purchase_price_change_approval_log (

  approval_level  INT,                            -- 第几级审批（1:部门经理 2:成本会计 3:财务经理 4:总经理）
  approver        VARCHAR(64),                    -- 审批人
  action          VARCHAR(16),                    -- approve/reject

```

### AI 分析 `purchase_price_change_ai_analysis`

```sql
CREATE TABLE purchase_price_change_ai_analysis (

  ai_status       VARCHAR(16) DEFAULT 'pending',  -- pending/analyzing/completed/failed
  ai_error_msg    TEXT,                           -- 分析失败原因

  -- 搜索关键词（联网比价用）
  search_keywords TEXT,                           -- 搜索关键词

  ai_analyzed_at  TIMESTAMP,
  created_at      TIMESTAMP DEFAULT NOW()
```

|---|---|---|
| 单据编号 | change_no | 自动生成 PC+日期+序号 |
| 标题 | title | 手填 |
| 供应商代码 | supplier_code | scm_supplier 下拉搜索自动带出 |
| 供应商名称 | supplier_name | 自动带出 |
| 电话 | phone | 自动带出 |
| 传真 | fax | 自动带出 |
| 联系人 | contact_person | 自动带出 |
| 地址 | address | 自动带出 |
| 顾客 | customer | 手填或从订单带出 |
| 顾客电话 | customer_phone | 手填 |
| 顾客传真 | customer_fax | 手填 |
| 采购联系人 | purchase_contact | 手填 |
| 日期 | change_date | 选日期 |
| 类型(涨价降价) | price_direction | 下拉选：涨价/降价/新报价 |
| 税率 | tax_rate | 手填 |
| 付款方式 | payment_method | 下拉选 |
| 结算方式 | settlement_method | 下拉选 |
| 附件 | attachments | 上传文件，JSON 存储 |
| 备注 | remark | 手填 |
| 签字意见 | signature_opinion | 审批通过后填写 |
| 序号 | item.seq | 自动编号 |
| 物料代码 | item.material_code | scm_material 下拉搜索自动带出 |
| 物料名称 | item.material_name | 自动带出 |
| 规格 | item.spec | 自动带出 |
| 单位 | item.unit | 自动带出 |
| 订货量 | item.order_qty | 手填 |
| 订货量到 | item.delivery_qty | 手填 |
| 原价 | item.old_price | **自动从 purchase_order 取最近采购价**（无历史记录时空置，允许手填） |
| 原价年月 | item.old_price_date | **自动取最近一次采购日期**（无历史记录时显示"--"） |
| 现价 | item.new_price | 手填 |
| 涨幅(%) | item.price_change_pct | **自动算** |
| 备注 | item.remark | 手填 |

### 原价自动带出的边界情况

| 场景 | 处理方式 |
|---|---|
| 该物料 + 该供应商有历史采购 | **自动带出最近一次采购价和采购日期** |
| 该物料有采购记录但供应商不同 | **自动带出最近一次采购价（不限供应商），但标注"非同一供应商"** |
| 该物料从未采购过 | **原价留空，原价年月显示"--"，允许手填** |
| 手填后再次修改 | **保留手填值，不再自动覆盖** |

> UI 上用一个图标或颜色区分"自动带出"和"手填"。自动带出的字段显示灰色背景，手填显示白色。

### 关键不同点（OA → 新系统）

| OA | 新系统 | 原因 |
|---|---|---|
| 原价手填 | **自动取最近采购价**（无历史时空置） | 减少人工错误 |
| 原价年月手填 | **自动带出** | 同上 |
| 涨幅手算 | **自动计算** | 同上 |
| 审批在 OA 里走 | **审批在系统内走** | 数据和流程一体化 |

## 四、审批流程

### 审批链

```
┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│ 申请人    │→  │ 部门经理  │→  │ 成本会计  │→  │ 财务经理  │
│ 提交     │   │ approval │   │ approval │   │ approval │
│          │   │ level=1  │   │ level=2  │   │ level=3  │
└──────────┘   └──────────┘   └──────────┘   └────┬─────┘
                                                    │
                                      ┌─────────────┴─────────────┐
                                      │                           │
                                 price_direction             price_direction
                                 = 降价                     = 涨价/新报价
                                      │                           │
                                      ▼                           ▼
                                  ┌──────┐                ┌──────────┐
                                  │ 归档  │                │ 总经理审批 │
                                  │      │                │ level=4   │
                                  └──┬───┘                └────┬─────┘
                                     │                         │
                                     ▼                         ▼
                                ┌──────────┐              ┌──────┐
                                │ ERP 同步  │              │ 归档  │
                                └──────────┘              └──┬───┘
                                                            │
                                                            ▼
                                                       ┌──────────┐
                                                       │ ERP 同步  │
                                                       └──────────┘
```

### 重要：用户交互提示

> **UI 必须明确提示**："降价审批流为 3 级（到财务经理），涨价/新报价审批流为 4 级（到总经理）"
> 在新建调价单选择类型后，实时显示审批链预览，避免申请人困惑。

### 5 级审批角色

| 级别 | 角色 | 系统角色码 | 触发条件 |
|---|---|---|---|
| 1 | 部门经理 | department_manager | 必走 |
| 2 | 成本会计 | cost_accountant | 必走 |
| 3 | 财务经理 | finance_manager | 必走 |
| 4 | 总经理 | general_manager | **只有涨价/新报价才触发** |
| - | 归档 | 系统自动 | 财务经理通过后（降价）或总经理通过后（涨价） |

### 驳回处理

```
任何一级审批人点"驳回" → status = rejected
  ├── 记录驳回日志（谁、哪一级、意见）
  ├── 通知申请人
  ├── 申请人修改后重新提交 → approval_level 重置为 1
  └── 旧审批记录保留（可追溯）
```

### 归档 + ERP 同步

```
审批通过后：
  1. status = approved → 调价生效
  1.5. 在 approval_log 里记录 action='submit' 的日志（审批人存申请人自己），流水线完整: 提交→通过→驳回
  2. 生成生效日志
  3. 异步同步 ERP：
     ├── 成功 → erp_sync_status = synced
     ├── 失败 → erp_sync_status = failed → 重试队列（每5分钟，最多3次）
     └── 3次都失败 → 通知管理员人工处理
  4. 通知申请人 + 相关人
```

## 五、AI 辅助分析

### 触发时机

```
调价单提交审批时 → 系统自动触发 AI 分析 → 审批人看结果
```

### 分析维度

| 维度 | 数据来源 | 展示方式 |
|---|---|---|
| 历史价格趋势 | purchase_order 表 12 个月历史采购价 | 折线图 |
| 外部比价 | LLM web_search 或爬虫 | 市场均价 + 价格区间 |
| AI 综合判断 | LLM 分析历史+外部数据 | 合理性判断 + 风险等级 + 一句话结论 |

### 分析结果存储

```
审批人打开调价单详情时，同时看到 AI 分析结果：
  ├── 📈 历史价格趋势图表（12个月）
  ├── 🌐 外部市场参考（来源：1688 / 行行查）
  └── 💬 AI 综合判断（风险等级 + 结论 + 依据）
```

### AI 分析时效性处理

```
问题：审批可能搁置几天，AI 分析结果可能过时

处理：
  1. 每次审批人打开详情页，判断 AI 分析是否超过 24 小时
     超过 → 提示"数据可能过时，建议刷新"
  2. 详情页提供"刷新 AI 分析"按钮（手动重新触发）
  3. 审批操作不阻塞（AI 分析中也可以审批）
  4. AI 分析状态展示：
     - pending     → "AI 分析中..."
     - completed   → 展示结果
     - failed      → "AI 分析失败，但不影响审批"
     - outdated    → "数据超过24小时，建议刷新"
```

### LLM 分析 Prompt 模板

```
你是采购价格分析专家，请分析以下调价：

物料：{material_name}（{material_code}）
供应商：{supplier_name}
原采购价：{old_price}，新采购价：{new_price}，涨幅：{pct}%

历史12个月价格趋势：
{history_trend}

外部市场参考价：
{market_comparison}

请给出：
1. 价格合理性判断（合理/偏高/偏低）
2. 风险等级（低/中/高）
3. 一句话结论
4. 详细分析依据（不超过100字）
```

### 联网比价方案

| 方案 | 实现 | 可靠性 | 状态 |
|---|---|---|---|
| LLM 内置搜索 | GPT-4 的 web_search 工具 | 中 | 优先使用 |
| 爬虫 | Python requests 爬 1688 | 低（反爬） | 备选 |
| 第三方 API | 生意社/行行查 | 高 | 后期接入 |

## 七、接口设计

| 接口 | 方法 | 说明 |
|---|---|---|
| `/purchase/price-change` | POST | 提交调价单（发起审批） |
| `/purchase/price-change` | GET | 调价单列表（分页/搜索/筛选） |
| `/purchase/price-change/{id}` | GET | 调价单详情（含子表+审批日志+AI分析） |
| `/purchase/price-change/{id}` | PUT | 编辑调价单（驳回后修改） |

### 审批配置存储

```
审批链放在 approval_config 表（可动态修改，不需要改代码）：

CREATE TABLE approval_config (
  id          SERIAL PRIMARY KEY,
  biz_type    VARCHAR(64) NOT NULL,          -- 'price_change'
  nodes       JSONB NOT NULL DEFAULT '[]',   -- 审批节点配置
  is_active   BOOLEAN DEFAULT TRUE,
  updated_by  VARCHAR(64),
  updated_at  TIMESTAMP DEFAULT NOW()
);

节点 JSON 格式：
[
  {"seq":1,"label":"部门经理审批","role":"department_manager"},
  {"seq":2,"label":"成本会计审批","role":"cost_accountant"},
  {"seq":3,"label":"财务经理审批","role":"finance_manager"},
  {"seq":4,"label":"总经理审批","role":"general_manager",
   "condition":{"field":"price_direction","op":"in","value":["涨价","新报价"]}}
]
```

> 审批配置修改后即时生效，不重启。管理员可在后台调整审批链（增减节点、更换角色），历史调价单不受影响（取发起时的快照）。

### 审批快照机制

```
为什么要快照：
  如果审批过程中管理员改了审批链（比如把第2级从成本会计改成财务总监），
  历史审批日志查出来"第2级是谁"会混淆。

怎么解决：
  1. 发起审批时，从 approval_config 读取当前审批链，计算本次走哪些节点，
     把**展开后的实际节点列表**（已计算 conditions，不含 condition 字段）存入 snapshot
  2. 审批过程中所有判断（当前级别是谁、有没有下一级）都读 snapshot，
     不再读 approval_config
  3. 审批日志 approval_log.approval_level 结合 snapshot 即可还原"当时谁审批的"
  4. conditions（涨价/新报价走总经理）只在发起时计算一次，结果固化到 snapshot
```

**快照 JSON 格式**（降价时，总经理被跳过）：
```json
[
  {"seq":1,"label":"部门经理审批","role":"department_manager"},
  {"seq":2,"label":"成本会计审批","role":"cost_accountant"},
  {"seq":3,"label":"财务经理审批","role":"finance_manager"}
]
```

**涨价时**（含总经理）：
```json
[
  {"seq":1,"label":"部门经理审批","role":"department_manager"},
  {"seq":2,"label":"成本会计审批","role":"cost_accountant"},
  {"seq":3,"label":"财务经理审批","role":"finance_manager"},
  {"seq":4,"label":"总经理审批","role":"general_manager"}
]
```

> 注意：快照**不存 condition 字段**，只存最终实际走的节点列表。

### 草稿功能

| 状态 | 说明 | 谁操作 |
|---|---|---|
| draft | 保存草稿，可随时编辑（含附件上传） | 采购员 |
| pending | 提交审批，表单锁定，不可编辑 | 采购员 |
| recalled | 撤回，回到可编辑状态 | 采购员 |

**草稿规则**：
- 草稿支持上传附件（文件立即存储到 `/uploads/price_change/draft/{change_id}/`，提交审批时归档）
- 草稿超过 **30 天**未提交，系统自动标记为过期（不再显示在列表），可手动恢复
- `created_at` = 创建时间，`submitted_at` = 首次提交审批时间（用于超时催办计算）

页面有"保存草稿"和"提交审批"两个按钮：
- 保存草稿 → status=draft，只保存不发起审批
- 提交审批 → status=pending，锁定表单，开始审批流转

## 十二、潜在风险点

| 风险 | 影响 | 处置 |
|---|---|---|
| ERP 同步接口不稳定 | 审批通过后同步失败，数据不一致 | 重试机制（3次，每5分钟）+ 人工补偿入口（手动重试+标记已同步） |
| LLM 分析可能延迟 | 审批人打开页面时 AI 结果还没出来 | 支持"AI 分析中"状态，不阻塞审批（审批人可以先看，AI 异步加载） |
| 角色权限数据不准 | 审批人匹配错误 | **开发前必须先确认角色 code**（待确认事项 #1） |
| 历史数据迁移量大 | 迁移影响上线时间 | 只迁移近 3 个月的在途单，已归档的不迁移 |
| 连接池耗尽 | 审批途中系统不可用 | 复用现有连接池（已优化过），审批接口用轻量级鉴权 |

## 十三、异常场景处理

| 场景 | 处理方式 |
|---|---|
| 审批人离职/不在岗 | 支持转审/代审，或管理员手动指定替代审批人 |
| 调价单提交后发现错误 | 审批中不可编辑，只能撤回后修改再提交 |
| 同一物料+同一供应商重复调价 | 允许，以最新审批通过的为准。提交时检测同一物料+同一供应商是否有在途调价单，提示申请人。不同供应商的同一物料互不影响 |
| ERP 同步失败后人工处理 | 提供管理后台手动同步入口 + 手动标记已同步 |
| 审批超时（超过5天未处理） | 系统自动催办（每天提醒审批人一次），超过10天通知管理员 |
| 并发审批冲突 | 使用乐观锁（version 字段）：approve/reject 接口 UPDATE 时 WHERE version=old_version，更新失败返回 409 Conflict 提示刷新重试。编辑草稿/提交审批不加锁（仅申请人操作，无冲突） |
| AI 分析失败 | 不影响审批流程，审批人可正常通过/驳回，UI 显示"AI 分析暂不可用" |
